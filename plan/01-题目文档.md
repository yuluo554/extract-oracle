# 题目文档：归档提取预言机（extract-oracle）

> **项目性质**：不参赛项目题（发布 GitHub **公开**仓库，署名 yuluo554）
> **目标产出**：`10-21-extract-oracle`（归档提取预言机：单文件可执行 + 纯本地 CLI）
> **版本史**：v1（2026-10-21 定稿）；依据查证基准日 **2026-10-21**（代理实际检索窗口 **2026-10-19T18:35Z–19:10Z**，见 `data/README.md` §1）
> **交付形态（唯一）**：**单文件可执行 + 纯本地 CLI**——只读归档、零网络、不依赖用户机器上的 Python/库/服务；不提供 GUI、不提供桌面窗口、不提供 Web 界面。
>
> **定位宣言**：现有工具只做"**单条规则检查**"或"**字段转储**"，没有一个输出**谁会写出什么名字、谁覆盖谁、哪个工具会拒绝**。本工具是**提取结果预言机**：输入一个 ZIP/TAR，逐条目预言它在 {Windows 资源管理器, Info-ZIP unzip, 7-Zip, libarchive, Python zipfile, macOS Finder, Linux} 上会变成什么名字、是否被覆盖、是否应用层不可见、是否被拒绝。**提取预言机不是体检器**——体检器告诉你"这个名字不合规"，预言机告诉你"这七个提取器里，有四个会把它写成别的名字，两个会互相覆盖，一个根本拒绝打开"。
>
> **品牌隔离**：本文档不提名本系列任何其他项目，不复制其他项目代码与文档，不与任何其他项目共享判定口径或数据。

## 1. 介绍

### 1.1 同一个归档，四个工具四种结果（✅ 本机实测，2026-10-19）

下表全部来自本机实测，非文献转述。实测环境：Windows 10.0.26200.8246 / NTFS（`LongPathsEnabled=1`）、Python 3.12.10（`unicodedata` 15.0.0）、7-Zip 25.01、Info-ZIP UnZip 6.00（Cygwin 构建，`UNICODE_SUPPORT`）、zipinfo 3.00、Perl `zipdetails`。fixture 均由 `struct.pack` 程序化合成。

| fixture | 构造 | Python `zipfile` | Info-ZIP `unzip` | 7-Zip 25.01 | `zipdetails` |
|---|---|---|---|---|---|
| `mismatch_name.zip` | LFH 名 `allowed.txt`、CD 名 `evil.txt` | **`BadZipFile` 硬失败** | 写 `evil.txt`，仅 stderr 警告 | 写 `allowed.txt`，报 `Errors: 1` 但**仍算成功** | 打 `ERROR`，但 **exit code = 0** |
| NFC/NFD `café` | 两条同名不同归一形 | 落盘 **2 个**（NTFS 不折叠） | 落 **2 个乱码名** | 落 2 个，NFD 那条改名 `cafe_.txt` | — |
| `Readme.txt` + `README.TXT` | 仅大小写不同 | 只剩 1 个，内容 `LOWER` | 只剩 1 个，内容 `LOWER` | 只剩 1 个，内容 `LOWER` | — |
| `CON.txt` / `aux.tar.gz` / `trailing. ` / `trailingdot.` / `colon:name.txt` | Windows 保留名、尾随点空格、冒号 | **全部写出**（`trailing` 被截断） | `:`→`_`，尾随点保留 | **全部加 `_` 前缀** | — |

> **由此得到本题存在的唯一理由**：同一个归档，**3 个工具写出 2 个不同文件名，1 个拒绝打开**。这不是"名字不合规"能概括的——`allowed.txt` 和 `evil.txt` 两个名字都完全合规，分歧发生在**读哪个头**。
>
> 另一条更隐蔽的实测：Python 写出的 `CON.txt`，在 PowerShell 里 `Test-Path -LiteralPath` 返回 `False`、`Get-Content` 报 *path does not exist*，但 `open()` 能读到内容 —— **文件存在，应用层拿不到**。这是"写得进但看不见"的最小可信证据，也是现有工具完全没有的分级。

### 1.2 竞品自认的缺口（✅ 原文引用）

本题不是从零想象需求，而是从**同期竞品自己写下的"不做"清单**里读出来的。2026-10-05 至 10-19 两周内，GitHub 冒出至少 4 个同题仓库：`cloudwallker/archive-preflight`（1★）、`Hhhxsss/zip-preflight`（0★）、`mehul82099/zip-preflight`（0★）、`mytestapp20261001-collab/zip-member-preflight`（0★）；其中两个功能相当完整（含 CI、pre-commit hook、Windows 右键菜单、HTML 报告）。

`Hhhxsss/zip-preflight` 的 `docs/rules.md` 原文（✅）：

> "No payload decompression, CRC/content validation, **local-header comparison**, **overlapping-entry detection**, alternate Unicode-path extra-field interpretation, nested archives, malware detection, symlink target validation, filesystem-specific 8.3 aliases, or extraction destination inspection is performed. Legacy filename encodings follow `zipfile` defaults (UTF-8 flag or CP437); **the tool does not guess encodings**."

`cloudwallker/archive-preflight` 的 `Policies` 表自认（✅）：

> "casefold is an **approximation**"；"normalization and casefold approximations"；"Native NTFS/APFS comparison tables… **require host testing**"。

这两段话合起来，把本题的三处阵地划得清清楚楚：
1. **双头差分与重叠检测**（"local-header comparison"、"overlapping-entry detection" 明写不做）；
2. **编码推断与 Unicode path extra field 解释**（"does not guess encodings" 明写不做）；
3. **真实文件系统折叠表**（竞品自认 casefold 只是近似、原生表"need host testing"）。

### 1.7 独特性拷问：为什么必须是工具，不是让 LLM 读一遍归档？

- **① 需要真实主机语义，不是语言常识**：NTFS 的折叠行为不能用 `str.lower()`/`casefold()` 近似。本机对 8 组字符对实测（✅）：

| 字符对 | casefold/upper 预测 | 实测 NTFS |
|---|---|---|
| `ı` / `I` | 冲突（simple_upper） | **不冲突** ✗ |
| `ſ` / `S` | 冲突 | **不冲突** ✗ |
| `ß` / `SS` | 冲突 | **不冲突** ✗ |
| `ß` / `ss` | 冲突 | **不冲突** ✗ |
| `İ` / `i` | — | **冲突** ✓ |
| `ǅ` / `Ǆ` | — | **不冲突** ✗ |
| `ω` / `Ω` | — | **冲突** ✓ |

**结论**：所有现存工具都用 `str.lower()`/`casefold()` 近似 NTFS，**会产生假阳性**（把不冲突的判成冲突）。这条不是知识题，是**主机探测题**——LLM 聊天答不对，因为它没在你的卷上测过。
- **② 需要可疑状态的可复现判定**：同一 fixture + 同一目标平台表 → 逐字节一致的 JSON。聊天每次措辞不同、漏项不可复现，无法进 CI 门禁。
- **③ 需要同时模拟多个提取器**：分歧本身就要求"多实现并排"的结构，单次对话给不出稳定的对照表。
- **④ 隐私边界**：归档常含未公开素材；纯本地零网络是硬约束。

**本题不做的"聪明事"**：不解压、不评分、不判恶意、不下结论"该用哪个工具"。

## 2. 任务要求

首期限定 **5 个模块**（MOD-1…MOD-5）。里程碑与模块的对应关系见 `plan/00` §六（M2 做 MOD-1，M3 做 MOD-3，M4 做 MOD-4，M5 做 MOD-2 收尾与 MOD-5）。所有模块共享四条纪律：

- **只读纪律**：**不解压到磁盘**。所有判定建立在"读字节 + 模拟目标平台语义"上；解压产物只允许出现在测试用的临时目录，且由测试自身清理。这条既是安全边界，也是"预言机"与"解压器"的分界线。
- **零网络纪律**：无任何网络调用；不下载真实样本；平台语义表随包分发。
- **口径单一定义**：退出码、三级可访问性定义、折叠规则来源、容器约定检查项，**只在 `data/README.md` §4 定义一次**；代码与文档只引用口径键。
- **确定性纪律**：同一输入 + 同一目标平台表 → 同一输出。输出默认**不含时间戳、不含随机 ID、不含本机绝对路径**；对象键序、数组排序（按 CD 条目偏移升序，同偏移按原始名字节字典序）、数值格式全部固定。

### 模块 ①：双头差分与重叠检测（MOD-1）

- **输入**：ZIP 文件（只读，按字节读）。
- **输出**：`findings[]`，`ruleId` 前缀 `structure.`，每个 finding 带 `{entryIndex, lfhOffset, cdOffset, lfhName, cdName}`。

| `ruleId` | 判定 |
|---|---|
| `structure.NAME_DIVERGES` | 同一 entry 的 LFH 文件名与 CD 文件名**字节不等** |
| `structure.CRC_DIVERGES` | LFH 与 CD 的 CRC32 不等 |
| `structure.SIZE_DIVERGES` | LFH 与 CD 的 compressed/uncompressed size 不等（含 data descriptor 场景的 `0x00` 占位判定） |
| `structure.FLAG_DIVERGES` | LFH 与 CD 的 general purpose bit flag 不等（尤其 bit 11 UTF-8） |
| `structure.LFH_OVERLAP` | 两个 entry 的 LFH 记录区间**字节区间相交**（不是名字相同，是物理重叠） |
| `structure.CD_COUNT_MISMATCH` | EOCD 声明的条目数与实际 CD 条目数不符（含 ZIP64 路径） |

- **依据纪律（关键）**：**不得引"规范要求 LFH 与 CD 一致"**——APPNOTE 6.3.10 未明文如此要求（逐字检索 "must be identical" / "SHOULD match" 均无命中）。判定一律引**实现选择**：unzip / libzip / Python `zipfile` 取 CD；libarchive 取 LFH（`libarchive#2695`，作者本人确认）。输出里每个 finding 附 `precedent` 字段写明依据来源。
- **验收**：四个 fixture 分别命中对应 code——
  | fixture | 应报 |
  |---|---|
  | `mismatch_name.zip`（LFH `allowed.txt` / CD `evil.txt`） | `NAME_DIVERGES` |
  | `alias_lfh.zip`（同名但 LFH 与 CD 的 extra field 不同） | `FLAG_DIVERGES` 或 `NAME_DIVERGES`（按构造断言具体项） |
  | `overlap.zip`（两个 LFH 区间相交） | `LFH_OVERLAP` |
  | `wrong_count.zip`（EOCD 计数与实际不符） | `CD_COUNT_MISMATCH` |
  另外三条工具行为断言进 CI：对 `mismatch_name.zip`，Python `zipfile` 必须抛 `BadZipFile`；`unzip` 的 stderr 必须含警告且落盘名为 `evil.txt`；`7z l`/`7z x` 取 `allowed.txt` 并报 `Errors: 1`。**这三条断言在 CI 的三个平台上跑，是本模块的"预言是否属实"的自证。**

### 模块 ②：文件名编码推断与 Unicode path extra field（MOD-2）

- **输入**：ZIP 条目（原始 `name` 字节 + bit 11 + extra fields）。
- **输出**：每条 entry 的
  1. `encoding.candidates[]`：候选编码列表（UTF-8 / CP437 / GBK / CP932 / CP949 / CP1251）及**可信度**（`high`/`medium`/`low`，判据见 `data/README.md` §4）；
  2. `upath`：是否带 0x7075（Info-ZIP Unicode Path）、是否带 0x6375（Unicode Comment）、是否带 0x0008（extended timestamp，仅记录不解释）；
  3. `predictedNames`：按各提取器实际解码策略预测的落盘名。
- **做法**：
  - bit 11 set → UTF-8（APPNOTE 6.3.10 D.2：**MUST** 为 UTF-8）；unset → 按历史 CP437 解释，**但**同时给出候选；
  - 0x7075 存在时：解析其 version/CRC/UTF-8 name；**CRC 对该 entry 原名字节校验**，通过才视为"覆盖判定有效"，不通过必须标 `upath_crc_mismatch` 并降级；
  - 预测规则按提取器固定：`unzip` 有 `UNICODE_SUPPORT` 时优先 0x7075，否则按 locale 解码；7-Zip 走自己的多编码猜测；Python 严格 bit11→UTF-8 否则 CP437；libarchive 有自己的转换表。
- **确定性纪律**：候选列表顺序固定为（UTF-8, CP437, GBK, CP932, CP949, CP1251），可信度只由字节统计决定，不用启发式随机。
- **验收**：
  - `zh_gbk.zip`（无 bit11，名字为 GBK 字节）：必须预测 **unzip 出乱码、7-Zip 出中文、Python 出另一套乱码**，三者互不相同；
  - `upath.zip`（bit11 未置位、带 0x7075 指向 `café.txt`）：必须预测 **7-Zip 出 `café.txt`**，而 **Python / unzip 出 `caf茅.txt`**（CP437 解释）。

### 模块 ③：跨平台落盘折叠（MOD-3）

- **输入**：模块 ①② 得到的"每个提取器会写出的名字"集合 + **目标平台**（`windows` / `macos` / `linux`）。
- **输出**：`collisions[]`，每条含 `{code, names[], writeOrder[], survivor, platform}`。

| `ruleId` | 判定 |
|---|---|
| `collision.CASEFOLD` | 两个名字在目标平台的大小写规则下相撞 |
| `collision.NFC` | 两个名字归一化后相撞（见下方"各平台口径"） |
| `collision.TRIM` | 名字经目标平台的尾随空格/点裁剪后相撞 |
| `collision.FILEDIR` | 同一路径既要当文件又要当目录 |

- **折叠表来源（不可让渡）**：
  - **Windows**：**必须用真实 NTFS `$UpCase` 表**——要么从卷读取（`FSCTL_GET_NTFS_VOLUME_DATA` 一族或直接读 `$UpCase` 元文件），要么用真机探测生成并**记录探测环境与卷标识**；**禁止用 `str.lower()`/`casefold()` 近似**（§1.7 的 8 组实测已证明近似会产生假阳性）。
  - **macOS**：NFC/NFD 采用 UAX #15 定义 + TN1150（"HFS Plus stores strings fully decomposed and in canonical order"）与 APFS 归一化不敏感的实现观察（**依据强度为中硬，须标注"逆向文档 + 实操，非 Apple 官方规范"**，见 `data/README.md` §5）。
  - **Linux**：不做大小写折叠；`/` 不可出现（pathname(7)）；按 `NAME_MAX` 与 `PATH_MAX` 的**字节**口径判长度（不是字符数）。
- **写序→存活者**：`writeOrder` 取 CD 顺序（各提取器均按 CD 顺序落盘）；`survivor` = 最后一个写入者，并附 `verdict`（`overwritten` / `renamed` / `skipped`）。**这一列是本题与"冲突列表"类工具的核心区别：它们只说"会冲突"，我们说"最后剩下谁"。**
- **验收**：
  - `case.zip`（`Readme.txt` + `README.TXT`）在 `--target windows` 下**必须**报 `collision.CASEFOLD`，且 `survivor = README.TXT`（与 §1.1 实测的"内容为 `LOWER`"一致）；
  - `norm.zip`（NFC `café` + NFD `café`）在 `--target windows` 下**不得**报冲突（NTFS 不做归一化），在 `--target macos` 下**必须**报 `collision.NFC`；
  - §1.7 的 **8 组字符对回归全部通过**（`ı/I`、`ſ/S`、`ß/SS`、`ß/ss`、`İ/i`、`ǅ/Ǆ`、`ω/Ω` 及一组对照），断言"用真实表判出的结果"与"casefold 近似判出的结果"在这几组上不同，且真实表结果与实测一致。

### 模块 ④：非法名与可访问性分级（MOD-4）

- **输入**：模块 ③ 的"会写出的名字" + 目标平台表。
- **输出**：每条 entry 的 `accessibility` 三级判定 + `reasons[]`。

| 级别 | 含义 | 判据 |
|---|---|---|
| `BLOCKED` | 写不进 | 目标平台在创建时就失败（Linux 名含 `/`、Windows 名含 `< > : " / \ | ? *` 或 0x00–0x1F、名字为空） |
| `WRITTEN_UNREADABLE` | **写得进但应用层打不开** | 落地成功，但按目标平台的应用层解析规则不可达（Windows 保留设备名，含带扩展名形式如 `NUL.txt`、含上标 ¹²³） |
| `WRITTEN_TRUNCATED` | **写出但名字已变** | 落地时名字被静默改写（尾随点/空格被裁剪、超长被截断） |

- **为什么第三级是差异点**：竞品的判定停在"合不合规"；本题区分"**合规与否**"和"**能不能被应用层拿到**"和"**拿到的还是不是原来那个名字**"三件事。`CON.txt` 落在三者之间——它不违规，它写入成功，它不是原来的名字，应用层拿不到。
- **依据**：Windows 非法字符 `< > : " / \ | ? *` 与 0x00–0x1F、保留设备名 CON/PRN/AUX/NUL/COM1-9/LPT1-9 **及带扩展名**（`NUL.txt` 等价于 `NUL`）与上标 ¹²³、尾随空格/点、`MAX_PATH=260`（含终止 NUL）、`\\?\` 前缀下 32767、**"the file system treats path and file names as an opaque sequence of WCHARs"（Windows 不做归一化）**。
- **验收**：
  - `reserved.zip` 的 `CON.txt` 在 `--target windows` 下**必须**报 `WRITTEN_UNREADABLE`，且 `reasons` 里带三条实测证据的机器可读形式（`Test-Path False` / `Get-Content error` / `open() readable`，作为 `evidence` 字段的固定枚举）；
  - `trailing.zip` 的 `trailing.` **必须**报 `WRITTEN_TRUNCATED`；
  - 边界：`NUL.txt`、`COM1.log`、`aux.tar.gz` 同判 `WRITTEN_UNREADABLE`；`readme.` 与 `readme` 同报 `WRITTEN_TRUNCATED` 且触发 `collision.TRIM`。

### 模块 ⑤：容器约定与长度预算（MOD-5）

- **输入**：ZIP 的 entry 序列 + extra field + 压缩方法 + 首文件字节。
- **输出**：`findings[]`，`ruleId` 前缀 `container.` / `budget.`。

| `ruleId` | 判定 | 依据 |
|---|---|---|
| `container.MIMETYPE_NOT_FIRST` | EPUB 的 `mimetype` 不是第一个文件 | EPUB 3.3 §4.3.3 "MUST include the mimetype file as the first file" |
| `container.MIMETYPE_COMPRESSED` | `mimetype` 被压缩或加密 | 同上 "MUST NOT compress or encrypt" |
| `container.MIMETYPE_EXTRA` | `mimetype` 带 extra field | 同上 "MUST NOT include an extra field"；ODF 1.2 part 3 §3.3 "shall not use an 'extra field'" |
| `container.MIMETYPE_PADDING` | `mimetype` 前后有 padding 或空白 | 同上 "MUST NOT contain any leading or trailing padding or whitespace"；**ODF 侧未明文禁止尾随换行，是从 media-type 相等约束推出，输出须标 `inferred`** |
| `container.UTF8_REQUIRED` | 容器语义要求文件名 UTF-8 但 bit 11 未置位 | EPUB 3.3 §4.3.2 "OCF ZIP containers MUST encode file system names using UTF-8" |
| `budget.PATH_OVER_260` | Windows 目标下完整路径超 260（含终止 NUL）且未启用长路径 | 依据见 `data/README.md` §4 |
| `budget.COMPONENT_OVER_255` | 单组件超 255（Linux 为字节、Windows 为 UTF-16 码元，分平台判） | 同上 |

- **容器识别**：按"是否存在 `mimetype` 条目 + `META-INF/container.xml`（EPUB）或 `mimetype` 内容为 `application/epub+zip` / `application/vnd.oasis.opendocument.*`"判定；识别不出就不做容器检查，**不得猜**。
- **交叉验证纪律**：`epubcheck` 与 ODF validator 只做 XML 层与包文档语义，**不做 ZIP 层**；本题与它们是互补关系，文档必须逐字写清这一点，不得暗示"更强"。
- **验收**：四个 mimetype fixture（`not_first.epub` / `compressed.epub` / `extra.epub` / `padding.epub`）**各命中一个 code**，且互不串报；`budget` 的两个 fixture 分别命中；容器识别对普通 ZIP 不产生任何 `container.*` finding（零误报基线）。

## 6. 边界与非目标

**不做（明确切割，每条附已覆盖者）**：

- **不解压到磁盘**——保持只读。这同时把本题与"归档安全审计"整体区隔开：解压即引入 zip slip / zip bomb 的攻击面，本题不碰。
- **不做 zip slip / zip bomb / 恶意软件检测**——已被填满：`snyk/zip-slip-vulnerability`（856★）、`ZOD`（918★）、`ronomon/zip`（258★）、以及 Python 标准库内置的绝对路径与 `..` 剥离。重复做只会是第四份更弱的实现。
- **不做嵌套归档与真实样本下载**——零网络是硬约束；嵌套归入扩展项且只做内存流。
- **不做文件清单一致性 / archive diff**——`diff -r` 与 BagIt（272★）已覆盖，且单文件 diff 即可完成，无内核。
- **不做安全打分 / 风险总分**——单一分数会掩盖具体分歧；输出只列可定位的条目与"谁会写什么名字"。
- **不做"该用哪个工具"的建议**——预言机只预言，不裁决。要不要改归档、要不要换工具，由用户决定。
- **不做 GUI / 桌面窗口 / Web 界面**——唯一形态是 CLI；右键菜单属于扩展项，且只是同一入口的薄壳，输出仍是文本/JSON。
- **不复制任何第三方代码**——平台语义表自行构造或真机探测生成，附录只引规范原句。

**首期范围限定**：ZIP 优先（含 ZIP64 的最小必要支持），TAR 列扩展；仅 `windows` / `macos` / `linux` 三个目标；仅 EPUB 3.3 与 ODF 1.2 的 mimetype 约定；不覆盖 8.3 短名与嵌套归档。

**隐私红线**：纯本地、零网络、零遥测；不收集、不上传任何归档内容；fixture 全部程序化合成，不含真实用户文件；报告中不写本机绝对路径。

**品牌隔离**：不提名、不复制本系列任何其他项目（尤其是做磁盘审计、文档去重、构建产物差异的三类项目），不共享数据与口径。

**诚实性要求（硬约束）**：

- **必须写清红海**：两周内 4 个同题仓库、其中 2 个功能完整——写进题面与决策记录，不许淡化成"少量同类"；
- 检索数据为软论据，必须带检索式与窗口，不得写成"业界首创/空白"；
- **APFS 依据强度须标注**：来自逆向文档与实操观察，非 Apple 官方规范；不得写成"Apple 规定"；
- **APPNOTE 依据须标注镜像来源**：官方原址不可达，用 GitHub 镜像，且不得据此编造"规范要求双头一致"；
- **ODF 尾随换行的推断须标 `inferred`**：原文未明文禁止；
- **不得用 casefold 近似冒充 NTFS**：折叠表来源必须可追溯（卷读取或真机探测记录）；
- 未实测的平台行为不得写成已达成（如 Windows 实际行为在非 Windows CI 上只能用表模拟，须在报告里标注"表模拟"而非"实测"）。

**免责**：本工具的输出是对**目标平台语义的模拟预测**，不是对某台具体机器的保证——卷格式、locale、注册表、文件系统驱动版本都会影响实际结果。预测与实际不符时，以实测为准，并把差异回填进平台表。
