## 四、决策记录补充（承接 `plan/00` §二）

| 日期 | 决策 | 结论与理由 |
|---|---|---|
| 2026-10-21 | **D10 骨架期 `check` 一律退出码 3，不产出空 findings** | 空 findings + 退出码 0 是"最坏的一种假绿"（用户以为查过、其实什么都没判）。宁可显式拒绝，也让 CI 能区分"没实现"与"没发现问题"。落地 = `capabilities.missing_core()` + `tests/test_cli_contract.py` 的变异断言。 |
| 2026-10-21 | **D11 方法论装订用 Python 门而非 Node 门** | 本机有 Node 24，但交付面承诺"零运行时依赖"，工具链也保持一致（纯标准库 Python）。判据集与模板同构，**只换实现语言不改判据**；模板本身明示"Python 项目按同一判据集重写即可"。 |
| 2026-10-21 | **D12 `pyproject` 用 `dynamic = ["version"]` 读 `__init__.__version__`** | 避免"版本号两处手抄"。构建产物自报的版本由 `--version` 输出，M6 起加第三条断言（产物自报 == 根模块版本）。 |
| 2026-10-21 | **D13 骨架先落 `inspect` 子命令** | `check` 未就绪期间需要一个**能真正跑通**的交付态命令（否则 README 里没有可演示的命令）。`inspect` 只报 EOCD 结构事实，**不产出任何 `ruleId`**，不与 MOD-1 的判定重叠。 |
| 2026-10-21 | **D14 三个 `--target` 在骨架期就进 `choices`** | 让"参数面"从第一天就固定，避免 M3 加 `--target` 时改动 CLI 契约（README 的 parser 反射对账要能从此稳定）。 |
| 2026-10-21 | **D15 `check` 的错误一律 stderr 单行 JSON** | stdout 不产出半份报告，CI 能直接 `jq` 断言；也避免"人读面与机读面混在一条流里"。 |
| 2026-10-21 | **D16 状态行判据要求"行内带状态 token"** | 门首版只匹配 `^\| M<k> \|`，把本项目的"里程碑内容表"（内容 / DoD 两列）与"变异验证表"也读成状态副本 → 报 M1–M6 全部不一致（假红）。正解 = 表格行 + 首格里程碑号 + **行内出现状态 token** 三条件同时成立；这是"判据张冠李戴"的正面修法，不是放宽断言（内容表里从不出现 ✅/⬜）。 |
